## §1 Overview

P1.6 ships `@cortex/feature-flags` as a thin consumer of F04. Per F04 D6 lock: F04 stays generic; flag-specific evaluation logic (`isEnabled` / `getVariant` / percentage rollout / kill switches) lives in P1.6's package. F04 stores flag definitions in a tenant-scoped namespace as opaque JSON blobs.

**Named first F04 consumer** — P1.6 is the canonical reference for F04 substrate consumption. The pattern P1.6 establishes (Zod schema registration → `registerConfigConsumer` adoption → `resolveConfig` for hot-path reads → `promoteDraft` for changes) is how every future F04 consumer integrates.

**4 initial flags to register in Slice A** per build-prompt:

- `admin-console.display-data-workspace-switcher` (gradual rollout)
- `analytical.cx-dd-01-beta` (Display Data workspace beta)
- `agents.planogram.v2-model` (model version rollout; A02 champion/challenger consumer per build-prompt §3316)
- `ingestion.csv-agent-v2` (CSV agent version control)

**Workspace-wide rule** (build-prompt §399 + CLAUDE.md line 740): "All new capabilities roll out behind a feature flag (`@cortex/feature-flags`)". P1.6 ships the substrate that makes this rule operationally true.

**Phase 1 deliverables:**

- `@cortex/feature-flags` package with `isEnabled` + `getVariant` server APIs.
- Non-React shim client helper (subscribe + getCachedValue + invalidate; framework-agnostic; React-hook recipe documented but not shipped).
- `registerConfigConsumer` adoption with `feature-flags` namespace + `ttl=30` (criterion 1's 30s propagation requirement).
- Per-flag default declared in registration; falls back to `false` if unspecified.
- 4 initial flags registered.
- Admin UI stub (minimal HTML page; no interactivity; SCR-04 ships full UI).
- Convention doc `docs/architecture/feature-flags.md` (lifecycle conventions; 6-month renewal rule; audit deviation rationale).
- Per-flag-change audit via F04's existing `CONFIG_VERSION_PROMOTED` (no new audit verbs).

**Phase 2 deferrals (per D8):**

- Full interactive Admin UI (SCR-04).
- Attribute-based targeting (requires AC01 user-attribute substrate; AC01 unshipped).
- Multi-replica cache invalidation broadcast (roadmap §1.12; needs Redis substrate).
- Per-evaluation audit emission (deviation rationale per D5).

## §3 D-locks

Eight cross-cutting decisions analogous to F04's D1-D14 (P1.6's smaller surface needs fewer locks). Locked at module-scoping PR (this PR); each slice's HOLD #1 may add `Q-NEW-FF-<slice>-N` items.

### D1 — Storage substrate: reuse `tenant_config_version` with `feature-flags` namespace

**Locked:** P1.6 stores flag definitions in F04's `tenant_config_version` table under namespace literal `tenant.feature-flags` (and `platform.feature-flags` for platform-default flags via Slice C resolver). NO new table.

**Naming reconciliation:** F04 D6 (`docs/planning/p1.4-f04-configuration-plane-scope.md` line 134) said `flags.*` namespace. F04 Slice E gate evidence + scope docs (lines 69, 76) said `feature-flags`. **`feature-flags` wins** — matches package name `@cortex/feature-flags`; hyphenated namespace convention; `flags.*` was earlier-draft naming superseded by Slice E gate evidence.

**Rationale:** F04 D6 explicitly directs feature flags to F04's substrate. New table duplicates work + violates D6.

**Alternatives rejected:**

- New dedicated `feature_flag` table (rejected per F04 D6).
- Different namespace name `flags` or `flag-definitions` (rejected — `feature-flags` matches package name).

### D2 — Type system for flag values: boolean + variant + numeric percentage

**Locked:** Phase 1 supports three flag value shapes:

- **Boolean** — `{ "type": "boolean", "default": false, "tenant_overrides"?: ... }` — `isEnabled` returns this.
- **Variant** — `{ "type": "variant", "variants": ["A","B","control"], "default": "control" }` — `getVariant` returns this.
- **Numeric percentage** — `{ "type": "percentage", "rollout_percentage": 25, "default": false }` — `isEnabled` returns true for `hash(userId+flagKey) < 0.25`.

Attribute-based targeting (per-user attributes other than rollout %) deferred to Phase 2.

**Rationale:** Build-prompt's flag-definition shape (`{ key, description, default_value, tenant_overrides, user_overrides, rollout_percentage }`) implies these three. Phase 1 ships only what's needed for the 4 initial flags.

**Alternatives rejected:**

- All four upfront (rollout %, targeting): targeting requires AC01 user-attribute substrate which is unshipped (P2.1).
- Boolean only: insufficient for `agents.planogram.v2-model` champion/challenger pattern.

### D3 — API shape: server APIs + non-React client shim + documented React-hook recipe

**Locked:** Phase 1 surface:

- **Server-side:** `isEnabled(client, tenantId, userId?, flagKey) → Promise<boolean>` + `getVariant(client, tenantId, userId?, flagKey) → Promise<string | null>`.
- **Client-side:** non-React shim `subscribe(flagKey, callback)` + `getCachedValue(flagKey)` + `invalidate(flagKey)`. Framework-agnostic.
- **React-hook recipe documented** in `docs/architecture/feature-flags.md` as an example (NOT shipped as code).

**Rationale:** No React infrastructure in workspace yet (zero React/JSX files; first React surface decision deferred). Build-prompt requires "React hook for client" but Phase 1 ships the shim that future React consumers wrap. SCR-04 (the Configuration screen) will lock the React-infra approach via a dedicated ADR-FE-001 when it ships.

**Alternatives rejected:**

- Ship full React hook in Phase 1: requires React-infra scaffolding (Vite, build target, possibly client-state library) — out of P1.6 scope.
- Server-only API in Phase 1: defers client-side propagation criterion (build-prompt acceptance 1).

### D4 — Override mechanism: config-only changes via F04 lifecycle

**Locked:** Flag value changes go through F04's `promoteDraft` on the `tenant.feature-flags` namespace. Runtime overrides (kill-switch via separate API) explicitly OUT of scope — would bypass F04's audit trail.

**Rationale:** F04 D6's "thin consumer" framing — P1.6 inherits F04's lifecycle for free. Every flag change has a `CONFIG_VERSION_PROMOTED` audit row + draft validation + rollback support.

**Alternatives rejected:**

- Runtime kill-switch API (rejected — defeats F04 audit purpose; if emergency kill needed, the config-promote round-trip already ships <30s propagation).

### D5 — Audit catalog: reuse `CONFIG_VERSION_PROMOTED`; deviation from build-prompt's "all flag evaluations logged"

**Locked:** No new audit verbs. Per-flag-CHANGE audit via F04's existing `CONFIG_VERSION_PROMOTED` (already emitted by `promoteDraft` on the flags namespace).

**Deviation from build-prompt:** Build-prompt's "All flag evaluations logged for auditability via audit events" is **untenable at scale** — every `isEnabled` call would emit audit, dwarfing F04's audit volume by orders of magnitude. Recommended interpretation: per-flag-change auditability (which F04 lifecycle provides for free) satisfies the spirit of the directive. Per-session-first-evaluation audit deferred as a Phase 2 enhancement if observability requirements surface.

**Convention doc** (Slice C) records this deviation explicitly so future readers don't re-derive it.

**Alternatives rejected:**

- New `FEATURE_FLAG_TOGGLED` verb: not needed; F04 captures every flag change through the existing catalog.
- Per-evaluation audit at every `isEnabled` call: rejected as untenable at scale.

### D6 — Default-value strategy: per-flag default declared in registration

**Locked:** Each flag's registration in `initial-flags.ts` declares its default value. The flag-definition Zod schema has `default: z.boolean()` / `z.string()` / `z.number()` per type. Falls back to `false` if unspecified.

**Rationale:** Matches build-prompt's `default_value` field. Per-flag granularity allows `agents.planogram.v2-model` to default to "champion" while `analytical.cx-dd-01-beta` defaults to false.

**Alternatives rejected:**

- Schema-default only (loses per-flag granularity).
- All-flags-default-to-false: matches build-prompt's "default_value" field but loses operator control over rollout state at registration time.

### D7 — Rollout strategy: percentage-based per-tenant Phase 1; attribute targeting Phase 2

**Locked:** Phase 1 supports percentage-based rollout via deterministic `SHA-256(userId + flagKey)` → percentage bucket. Same `(userId, flagKey)` always returns same bucket across calls (stable assignment).

Attribute-based targeting (per-user attributes other than identity) deferred to Phase 2 because it requires AC01's user-attribute substrate which is unshipped (P2.1).

**Rationale:** SHA-256 truncated is deterministic + collision-resistant + simple. Build-prompt's `flag.isEnabled(tenantId, userId)` signature accepts userId for exactly this purpose.

**Alternatives rejected:**

- Random rollout (rejected — not stable across calls; user sees flicker).
- Tenant-only (no per-user variance): insufficient for gradual rollout pattern.
- MD5 / weaker hashes: SHA-256 is the workspace cryptographic-hash convention.

### D8 — Phase 2 boundary explicit

**Locked:** Phase 1 P1.6 ships:

- `@cortex/feature-flags` package with `isEnabled` + `getVariant` server APIs (D3).
- Non-React client shim + documented React-hook recipe (D3).
- `registerConfigConsumer` adoption with `feature-flags` namespace + `ttl=30` (D1).
- 4 initial flags registered (Slice A).
- Admin UI stub (Slice C).
- Convention doc `docs/architecture/feature-flags.md` (Slice C).

Phase 2 deferrals:

- Full interactive Admin UI (SCR-04 Configuration screen).
- Attribute-based targeting (requires AC01 user-attribute substrate; P2.1 unshipped).
- Multi-replica cache invalidation broadcast (roadmap §1.12; needs Redis substrate).
- Per-evaluation audit emission (per D5 deviation; deferred unless observability requires).
- React-hook code (Phase 1 ships shim + recipe; React infra ADR-FE-001 lands at SCR-04).

**Migration path:** Each Phase 2 wire-up is additive. The Phase 1 surface is stable; only new APIs land.

## §4 Q-NEW recommendations

Pre-defined per-slice items where module-scope can helpfully constrain. Slice-level Q-NEW items finalize at each slice's HOLD #1.

- **Q-NEW-FF-A-1** — Flag-definition Zod schema shape. Discriminated union by `type` field (`boolean` / `variant` / `percentage`)? Lean: yes; Zod's discriminated-union support gives compile-time exhaustiveness. Lock at Slice A HOLD #1.
- **Q-NEW-FF-A-2** — Hash function for percentage rollout. Lean: SHA-256 truncated (deterministic + collision-resistant + simple; workspace hash convention). Lock at Slice A HOLD #1.
- **Q-NEW-FF-B-1** — Client API shape for non-React shim. Lean: `subscribe(flagKey, callback) → unsubscribe` + `getCachedValue(flagKey)` + `invalidate(flagKey)`. EventEmitter-style under the hood OR Symbol-based subscription registry. Lock at Slice B HOLD #1.
- **Q-NEW-FF-C-1** — Admin UI stub shape. Lean: minimal static HTML in `packages/feature-flags/admin-stub/index.html` listing flags + their current values; NO interactivity Phase 1 (SCR-04 ships full UI with mutations). Lock at Slice C HOLD #1.
