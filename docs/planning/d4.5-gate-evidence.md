## §1 D.4.5 reconciliation surfaces (discovered during gate run)

Three real surfaces emerged that the brief + HOLD #2 build plan
didn't anticipate. Captured here before the §2 gate-evidence curls
because they shaped what landed in the squash.

### §1a URL drift: route vs. env-var

Pre-D.4.5: TF env-var `PROVISIONING_WORKER_URL` was set to
`{service-url}/v1/_workers/provision` (set during D.4 declarative-
worker-URL work; matches the test-helper convention). HOLD #2 plan
used `/v1/_workers/provisioning` for the new route. Mismatch —
Cloud Tasks would dispatch to `/provision` (the env-var path) but
the route would be at `/provisioning`. **Fixed:** route path
aligned to `/v1/_workers/provision` (no `-ing`); matches env-var

- test helper.

### §1b OIDC token gap in `dispatchCloudTask`

`packages/tenant-context/src/cloud-tasks.ts` was written without an
`oidcToken` field on the dispatched task. Cloud Tasks therefore
dispatched as anonymous → Cloud Run's invoker IAM (D.5) returned
403 for every retry. Symptom: `gcloud logging read` showed
repeated `httpRequest.status=403` on the worker URL with no
hand-off to the Hono app. **Fixed:** added
`oidcServiceAccountEmail?: string` to `DispatchOptions`, threaded
through to the task spec's `httpRequest.oidcToken.serviceAccountEmail`.
`tenants.provision` + `tenants.offboard` (forward-compat for D.6)
now read `CLOUD_TASKS_INVOKER_SA_EMAIL` from env + pass it through.

This was **always broken** for any deployed worker route. D.2's
key-rotation worker route was deployed pre-D.5 + never exercised
via real Cloud Tasks dispatch (only direct HTTP from tests); the
gap stayed dormant. D.4.5 first hits it because the provisioning
route is the first dispatched-via-Cloud-Tasks worker post-D.5.

### §1c Self-actAs IAM grant missing

After §1b's fix, Cloud Tasks' first dispatch attempt failed inside
the SDK with `7 PERMISSION_DENIED: The principal lacks IAM
permission "iam.serviceAccounts.actAs" for the resource
"tenant-lifecycle-runtime@sevyn8-cortex-dev.iam.gserviceaccount.com"`.
Cloud Tasks impersonates the runtime SA to mint OIDC tokens, but
the runtime SA has to have `actAs` on itself (the `oidcToken.serviceAccountEmail`
target) for that impersonation to work. Per Q-NEW-D-11 Option 1
(dispatcher = OIDC-subject = runtime SA), this is a self-actAs
grant. **Fixed:** added
`google_service_account_iam_member.lifecycle_runtime_self_user` in
`infra/terraform/environments/{dev,staging,prod}/main.tf` granting
`roles/iam.serviceAccountUser` (which contains `iam.serviceAccounts.actAs`)
to the runtime SA on itself. Applied to dev (`Apply complete!
Resources: 1 added, 0 changed, 0 destroyed`); declared for staging

- prod (deferred per roadmap §2.5a billing).
