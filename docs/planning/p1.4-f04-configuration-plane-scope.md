# F04 Configuration Plane — Module scope

> **P1.4** — Configuration Plane. The tenant-facing config layer. Every tenant-scoped setting lives here; every configuration change goes through F04.
>
> Scoped 2026-05-09 in the same session that closed F03 (Slices A + B + B.5) and enforced branch protection. D1-D14 locked at HOLD #0; Q-NEW-F04-\* held for slice-start HOLDs. This doc is the Phase 1 planning artifact; per-slice scope docs (`f04-slice-{A,B,C,D,E}-scope.md`) populate at each slice's HOLD #1.

## Context

F04 is the canonical configuration layer for the entire platform. Theme tokens, locale + i18n, feature flags, screen-registry overrides, hierarchy schema, retention policies, quality rule libraries, vertical-package selection, and SCD policies (F03 Slice C consumer) all live as tenant-scoped configuration in F04. Every change goes through a draft → validate → promote → rollback lifecycle with audit-trail emission and impact-analysis gating; reads are layered (workspace → tenant → platform fallback) and cached for sub-10ms p99 against the build-prompt acceptance criterion.

The build-prompt (`docs/build-prompts/cortex_build_prompts_v3.md` §P1.4) is canonical. Four scope items, all P1 deliverables: (1) configuration store with hierarchical KV in Postgres JSONB + Zod-validated namespace schemas; (2) lifecycle (draft/validate/promote/rollback); (3) impact analysis pre-promotion; (4) configuration-as-code Git sync (stubbed for Phase 2). UI is explicitly **out** — `SCR-04 Tenant Configuration & Theme` ships the admin surface later.

F04 is the **second multi-phase F-feature in the Cortex roadmap** (F03 was the first). Slices A + B + C + D + E are sequenced in P1.4; **F03 Slice C unblocks at F04 Slice B close** (operationally-safe lifecycle for SCD policy changes) and lands inside P1.4 itself, not P1.5. Module total effort: 26-42 hr across 5 slices, comparable to F03 module nominal (30-46 hr).

## §0 Substrate inventory — what's already in place

`tenant_config_version` table shipped at F01 Slice A (`services/foundation/migrations/0007_control_plane_tables.sql:74-90`):

```sql
CREATE TABLE tenant_config_version (
  id                  uuid         PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id           uuid         NOT NULL REFERENCES tenant(id) ON DELETE RESTRICT,
  version_number      integer      NOT NULL,
  config_json         jsonb        NOT NULL DEFAULT '{}'::jsonb,
  created_at          timestamptz  NOT NULL DEFAULT date_trunc('millisecond', now()),
  created_by_user_id  uuid,
  UNIQUE (tenant_id, version_number)
);

ALTER TABLE tenant_config_version ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_config_isolation ON tenant_config_version
  FOR ALL TO public
  USING (tenant_id = cortex.current_tenant_id())
  WITH CHECK (tenant_id = cortex.current_tenant_id());
```

**Shape mismatch with F04's per-namespace versioning model.** As shipped, this table is row-per-`(tenant, version_number)` with the **entire config as a single JSONB blob**. Operator's locked D1 shape is row-per-`(tenant, namespace, version_number)` so that a theme change in `tenant.*` doesn't bump the version of `platform.*`, and Zod validation can be scoped per-namespace. Slice A's first migration reshapes the table — see D9 below for migration details.

**F02 writers already touch this table:**

- `packages/tenant-context/src/tenants.ts:355` — provisioning seeds `version_number=1` with empty `config_json: {}` per Q-OPEN-4 (IC01 vertical-package seed deferred to P5.2).
- `packages/tenant-context/src/export-archive.ts:70,257,280` — exports all `tenant_config_version` rows for a tenant during offboarding.
- `packages/tenant-context/src/provisioning-worker.ts:316` — DELETEs `tenant_config_version` rows during termination (`ON DELETE RESTRICT` FK requires explicit deletion).

All three call sites adopt `namespace = 'tenant'` for the v=1 seed during the Slice A migration; no functional change to F02's behaviour, only column shape.

**Audit-events catalog convention** (per `packages/tenant-context/src/audit-actions.ts`): each module owns its action catalog declared via `registerAuditActions([...] as const)` in a side-effect-free file. F04 ships its own at `packages/config-plane/src/audit-actions.ts`. Six verbs locked at HOLD #0 (D11):

- `CONFIG_DRAFT_CREATED` (CREATE)
- `CONFIG_DRAFT_UPDATED` (UPDATE)
- `CONFIG_DRAFT_VALIDATED` (READ + result metadata)
- `CONFIG_DRAFT_DISCARDED` (DELETE)
- `CONFIG_VERSION_PROMOTED` (CREATE — derivative)
- `CONFIG_VERSION_ROLLED_BACK` (CREATE — derivative)

**Bi-temporal substrate explicitly NOT used.** F03's SCD trigger + `at_time_t` predicate are for entities whose validity changes over business-time independent of system-time. Configuration validity is system-time only ("this version was active in the system from time X to Y") — no business-time axis. Bi-temporal would be over-engineering. See D2 below.

## §1 Cross-cutting decisions D1-D14 — locked at HOLD #0

### D1 — Storage shape: row-per-`(tenant, namespace, version_number)`

**Locked: D1a** (reshape existing `tenant_config_version`).

The blob in `config_json` is the namespace tree. Reshape adds `namespace text NOT NULL` and `parent_version_id uuid REFERENCES tenant_config_version(id)`; UNIQUE moves from `(tenant_id, version_number)` to `(tenant_id, namespace, version_number)`. F02's three call sites adopt `namespace = 'tenant'` for the v=1 seed in the Slice A migration.

**Alternatives considered:**

| Option                                                                                                                                 | Rejected because                                                                                                                |
| -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **D1b** — keep `tenant_config_version` as full-tree-blob; add new `tenant_namespace_config_version` for F04's per-namespace versioning | Two tables conceptually overlap (both are "tenant config") → future debt; doubles RLS surface; F04's reads have to span both.   |
| **D1c** — row-per-leaf-key (etcd / consul model)                                                                                       | Over-granular; doesn't fit "Zod schemas per namespace" build-prompt directive (validation atom is the namespace, not the leaf). |

**Rationale for D1a**: build-prompt's "config_version rows with parent pointer" maps cleanly to per-namespace versioning. The reshape is mechanical (one column add + UNIQUE change + 3 F02 call site adjustments). Backfill for existing rows is trivial — `tenant_config_version` rows seeded by F02 contain `config_json: {}`; the reshape sets `namespace='tenant'` for all backfilled rows.

### D2 — Versioning model: append-only chain with parent pointer

**Locked: build-prompt directive.** Every change creates a new `tenant_config_version` row; `parent_version_id` references the row this one supersedes. `version_number` stays for human-friendly ordering; `parent_version_id` formalizes the chain (handy for rollback).

**Alternatives explicitly rejected:**

- **Reuse F03 bi-temporal substrate** — config has system-time only; no business-time axis. SCD trigger would emit empty motion (every "valid_time" would be `[now, NULL)` always). Over-engineering.
- **Current-state table + history table** — F02's audit-event chain already provides history-via-events; second history table duplicates that. Single append-only versioned table is sufficient.

### D3 — Drafts: separate `config_draft` table

**Locked: build-prompt directive** (`config_draft row, visible only to author`).

Drafts and versions have different lifecycles: drafts are mutable, discardable, and may carry validation-error metadata; versions are immutable (audit chain). Separate tables keep the invariants clean.

**Sub-lock: author-only visibility.** AC01 hasn't shipped `cortex.current_user_id()` yet, so Phase 1 implementation uses an explicit `created_by_user_id` filter in app code:

```ts
// Phase 1 — pre-AC01
const drafts = await db.execute(sql`
  SELECT * FROM config_draft
  WHERE tenant_id = ${tenantId}
    AND created_by_user_id = ${callerUserId}
`);
```

Post-AC01, this upgrades to an RLS policy referencing `cortex.current_user_id()` via a follow-up migration. The fallback is documented in the Slice B migration header so future authors don't re-derive it.

### D4 — Layered resolution: lazy at read-time + per-process LRU

**Locked: lazy resolve at read-time + per-process LRU on resolved blob with TTL invalidation on promote/rollback.**

`getConfig(ctx, namespace)` walks layers per call (workspace → tenant → platform fallback; workspace deferred per D14, so Phase 1 walks tenant → platform only). The resolved blob caches in a per-process LRU keyed on `(tenant_id, namespace)`; promote/rollback invalidates the entry.

**Alternatives considered:**

- **Materialized resolve at promote-time** — pre-compute the resolved blob per (tenant, namespace) at promote, store as a separate row. Rejected: premature; eager materialization fights the lazy-on-read shape; cache invalidation on promote is simpler than materialization replacement.
- **Hybrid (lazy + materialize-on-hot)** — materialize for high-read namespaces only, lazy for cold. Rejected for Phase 1: adds dispatch logic for negligible incremental benefit at single-replica deploy. Future optimization tracked at roadmap §1.12 (D10).

Phase 1 single-replica deploy makes read-after-write consistency on the in-process LRU trivial. Distributed invalidation (cache-bust across Cloud Run replicas on promote) is the future optimization path; Redis-backed cache deferred per D10.

### D5 — Impact analysis: build-time consumer registration

**Locked: build-time consumer registration via `registerConfigConsumers(...)`.**

Each consumer module exports a `CONFIG_CONSUMERS` constant via the helper at module init. Side-effect-free at top level (parallel to `registerAuditActions` precedent in `@cortex/audit-events`). F04's `promote()` queries the union registry to compute impact ("changing `tenant.theme.primary_color` affects: UX01 widget X, SCR-Y dashboard, vertical-package Z").

**Alternatives considered:**

- **Runtime grep / static analysis** — scan codebase at promotion time for namespace references. Rejected: fragile (misses dynamic key construction; brittle against minor refactors); requires a build step at runtime.
- **Manual metadata in scope docs** — consumers declare deps in their planning docs. Rejected: decays the moment a consumer is added/removed; no mechanical enforcement.

Per-consumer registration cost is one call at module init; benefit accumulates across the consumer set. Pattern matches the precedent set by audit-actions.

### D6 — Feature-flag integration: P1.6 thin layer on F04

**Locked: P1.6 ships `@cortex/feature-flags` as a thin consumer of F04. F04 stays generic.**

Build-prompt confirms: _"Build a feature flags service on top of F04."_ Flag-specific evaluation logic (segmentation, rollout %, kill switches, percentage-based traffic split) lives in P1.6's package. F04 only stores flag definitions in the `flags.*` namespace as opaque JSON blobs.

**Implication for F04:** no flag-specific code paths anywhere in F04. Feature flags are one of many namespaces; `getConfig(ctx, 'flags')` returns a generic JSON object that P1.6 interprets.

### D9 — `tenant_config_version` evolution path: reshape (Slice A migration)

**Locked: Slice A migration reshapes the existing table.** Migration adds:

```sql

  ADD COLUMN namespace text;

UPDATE tenant_config_version
  SET namespace = 'tenant'
  WHERE namespace IS NULL;

ALTER TABLE tenant_config_version
  ALTER COLUMN namespace SET NOT NULL;
```

The migration is **idempotent for the existing single-tenant Phase 1 deploy** — one tenant, one row, all rows backfill to `namespace='tenant'`.

### D10 — Caching strategy: in-process LRU + TTL for Phase 1

**Locked: in-process LRU + TTL.** Redis-backed distributed cache deferred to roadmap §1.12 (new entry; lands in this PR alongside the scope doc).

Sub-10ms p99 against in-process cache is trivial. Trigger to revisit (per §1.12): F04 read traffic crosses the threshold where multi-replica cache divergence becomes operationally noticeable (e.g., a developer toggles a feature flag and one replica serves stale value for >1s).

LRU sizing: per-tenant resolved-blob size ~1-100KB; cache key `(tenant_id, namespace)`. Default capacity 1000 entries (~10MB worst case); TTL 60s; promote/rollback paths invalidate entries explicitly via cache key.

### D12 — Schema registry: dynamic `registerNamespaceSchema(namespace, schema, { version })`

**Locked: dynamic registration with EXPLICIT schema_version on registration.**

Workspace packages stay at `0.0.0`; package-version-as-schema-version doesn't work. Schema version is a separate explicit number stored alongside each draft + version row:

```sql
ALTER TABLE tenant_config_version
  ADD COLUMN schema_version integer NOT NULL DEFAULT 1;

ALTER TABLE config_draft  -- created in Slice B
  ADD COLUMN schema_version integer NOT NULL;
```

```ts
// at consumer module init
registerNamespaceSchema('platform.theme', PlatformThemeSchema, { version: 1 });

// later, schema evolves
registerNamespaceSchema('platform.theme', PlatformThemeSchemaV2, { version: 2 });
// drafts created against v=1 keep validating against v=1 even after v=2 ships
```

Drafts pin to the schema_version that existed at draft-create time. Promote validates against that pinned version. This isolates in-flight drafts from schema bumps.

**Alternatives considered:**

- **Static module-level schemas** — `export const PLATFORM_NAMESPACE_SCHEMA` from each consumer; F04 imports via barrel. Rejected: import-graph cycle risk; static imports from F04 to every consumer module is the wrong direction (consumers should depend on F04, not the reverse).
- **Package version as schema version** — workspace packages all `0.0.0`; doesn't carry meaningful version info.

### D13 — Promote concurrency: optimistic with parent_id check

**Locked: optimistic concurrency.**

```ts
INSERT INTO tenant_config_version (
  tenant_id, namespace, version_number, parent_version_id, config_json, schema_version
)
SELECT $1, $2, $existing_version_number + 1, $existing_id, $3, $4
FROM tenant_config_version
WHERE tenant_id = $1
  AND namespace = $2
  AND id = $expected_current_id  -- OR upper(supersession) IS NULL semantically
RETURNING id;
```

Conflict (zero rows returned because parent moved) → caller retries the draft on top of the new parent. Matches F02's audit-chain idiom.

**Pessimistic alternative rejected:** advisory locks (`pg_advisory_xact_lock(tenant_id::int, namespace_hash)`) work but block; optimistic surfaces conflict at the API layer where the caller can decide retry semantics. Two-seat repo doesn't see meaningful contention; if Phase 2 traffic justifies, switch to pessimistic via a Slice-B-future migration.

### D14 — Workspace namespace: deferred per first-consumer

**Locked: Phase 1 ships platform → tenant resolution only.** Workspace layer wires when the first workspace-override consumer arrives.

Build-prompt mentions `workspace.*` namespaces but doesn't list a Phase 1 consumer that requires per-workspace overrides. ADR-DB-001's deferral pattern applies: don't ship the substrate until a consumer needs it. Slice C's resolution layer is platform → tenant; workspace insertion-point documented in Slice C's exit criteria (so it's clear what the future consumer will need to wire).

**Three resolution paths explicitly recorded** for the future consumer:

- **(a)** Per-workspace namespace `workspace.<wid>` containing the full tree
- **(b)** Theme/i18n/etc. as namespaces, scoped per-workspace via path segment (`workspace.<wid>.theme`)
- **(c)** Phase 1 = no workspace-scoped configs; revisit when first override use case arrives

Slice C ships (c). When F04 module closes, the operator picks (a) vs (b) at the first workspace-consumer kickoff.

### Slice D — Impact analysis + breaking-change blocker

**Effort:** 6-10 hr. **Status:** P1.4 fourth slice.

**Deliverables:**

- `packages/config-plane/src/consumer-registry.ts` — `registerConfigConsumers(consumers)` helper. Each entry: `{ namespace, key, consumer_module, breaking_change_policy }`. In-memory registry, per-process.
- `packages/config-plane/src/impact-analysis.ts` — `analyzeImpact(ctx, draftId)` queries the union registry for consumers of the namespace + key paths the draft touches; returns `ImpactReport { affected_consumers, breaking_changes, warnings }`.
- Breaking-change definitions: (1) removing a key that any consumer registered against; (2) Zod schema change that makes a previously-valid value invalid; (3) any change to a key flagged `breaking_change_policy: 'block'` in the registry.
- `promoteDraft(...)` (from Slice B) becomes impact-aware: if `breaking_changes.length > 0` AND no explicit `confirmBreakingChanges: true` option, throws `ImpactBlockedError`.
- Confirmation UX: `promoteDraft(ctx, draftId, { confirmBreakingChanges: true })` overrides; emits enriched audit metadata (`override_reason`, `affected_consumers`).

**Acceptance (build-prompt directive):**

> Impact analysis identifies all downstream consumers before a breaking change

## §5 Risk register

### F02 reconciliation surface

`tenant_config_version` is touched by 3 F02 call sites. Slice A's reshape migration must keep F02's behaviour structurally same:

- **`packages/tenant-context/src/tenants.ts:355`** — provisioning seeds v=1 with `config_json: {}`. Adopts `namespace = 'tenant'` + `schema_version = 1`. INSERT statement column-list updates only.
- **`packages/tenant-context/src/export-archive.ts:70,257,280`** — exports `tenant_config_version` rows. Selects `*` already; new columns ride along automatically. Export-archive consumers see the namespace + schema_version + parent_version_id columns appear.
- **`packages/tenant-context/src/provisioning-worker.ts:316`** — DELETEs by `tenant_id`. Unchanged structurally.

**Mitigation:** Slice A's migration commit MUST re-run the existing 68-test foundation suite + the export-archive test path. Any test that does `SELECT *` from `tenant_config_version` and asserts column ordering is at risk; mitigation is to assert by column name, not position.

### §1.9 audit-payload-size pressure-signal

F04 Slice B's emission rate (4 events per draft → promote round-trip × N consumers) could be the first observed pressure signal that triggers roadmap §1.9 (audit payload size enforcement). Each event's `after_state` may carry the full namespace tree (potentially 1-100KB JSONB).

**Mitigation:** Slice B's planning explicitly cross-references §1.9 — if the gate evidence shows aggregate emission size approaches the 64KB warning threshold per event, the §1.9 work triggers immediately rather than being deferred. F04 gate evidence will note the per-event emission size.

### AC01 dependency for D3 author-only visibility

D3 sub-lock: Phase 1 author-only-draft uses explicit `created_by_user_id` filter in app code; Phase 2 upgrades to RLS once AC01 ships `cortex.current_user_id()`. The fallback works but is enforced at app-layer only — a misbehaving SQL query that queries `config_draft` without the filter would see all drafts.

**Mitigation:** Slice B's `config_draft` table comment + migration header explicitly document the fallback + AC01 dependency. Slice B test fixtures include a "bypass" test asserting that direct SQL queries without the filter DO return cross-author rows (proving the AC01 upgrade is necessary). Post-AC01 migration is a follow-up commit, not a Phase 1 work item.

### §1.12 (new) Redis distributed cache scaling trigger

Phase 1 in-process LRU works for single-replica deploy. Multi-replica deploy (Cloud Run scaled out) would see promote-time cache invalidation hit only the local replica; other replicas continue serving stale config until TTL expires (60s).

**Mitigation:** roadmap §1.12 (this PR adds the entry) tracks Redis-backed distributed cache. Trigger: first observed multi-replica cache divergence (e.g., feature-flag toggle visible inconsistently). Phase 1 single-replica deploy doesn't experience this.
